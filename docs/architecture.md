# Estella 多游戏项目模板设计

这份设计面向使用 Estella 的多款游戏。首版已经接入启动装配、页面导航、模拟会话、原生场景、资源交付、设置、版本化存档和发布回归。下面的目录给出扩展位置，`platform/`、`assets/shared/` 等目录在有实际内容时建立。新建项目、运行和导出命令见[使用说明](../README.md)。

## 目录与依赖

```text
src/
  main.ts                 运行入口，调用 app 启动
  components.ts           编辑器组件入口，汇集本作启用的组件声明
  app/                    本作装配，登记游戏标识、模块、平台实现、启动流程
  framework/              每款游戏都可以沿用的运行规则
    flow/                 流程切换、暂停和恢复、场景退出清理
    ui/                   页面导航、弹窗顺序、返回和焦点
    content/              资源组加载、进度、失败重试、使用期
    storage/              存储键、存档读写约定、版本迁移接入
  modules/                可独立选用的公共功能，按功能纵向组织
    settings/             示例：设置模型、设置页、音量与语言偏好的应用
  game/                   这款游戏的规则、流程定义和内容标识
    features/             每个玩法拥有自己的组件、系统和界面绑定
  platform/               接入特定宿主才需要的实现，如登录或触感反馈
  gen/                    Luban 生成的 TypeScript
assets/
  scenes/main.esscene     当前启动场景
  boot/                   首屏和加载失败时仍可显示的资源
  shared/                 多个模块确实共用的字体、图标、材质等
  modules/                与可选模块同名的预制体、图像和音效
  game/                   按玩法、章节或其他可独立进入的内容组织
  data/                   Luban 生成的数据
config/luban/             表定义、数据源与生成配置
tools/                    生成、资源引用校验、构建与报告脚本
tests/                    规则测试、存档样本、编辑器及导出包的冒烟用例
docs/                     开新项目、升级模板、构建发布的说明
```

**依赖从装配入口流向具体功能。** `app` 选择本作使用的 `game`、`modules` 和 `platform` 实现。玩法可以调用已选模块的公开接口。通用模块只使用框架、引擎和已声明的依赖。框架本身只依赖 Estella 及基础库。平台能力由使用方定义所需接口，具体宿主实现在启动时传入。引擎已屏蔽平台差异的 API 可以直接使用。

一个功能初期可以只有一个文件。需要拆开时，把它的模型、ECS 系统、界面绑定、测试样本放在同一功能名下。编辑器通过 [components.ts](../src/components.ts) 读取组件声明，该入口适合导入各模块的组件定义。系统注册、平台初始化和其他运行时行为从 [main.ts](../src/main.ts) 进入。

### 三种分包各解决一件事

| 边界 | 建议 | 如何验证 |
|---|---|---|
| 源码模块 | 同一玩法的规则、组件和界面绑定放在一起，仅从公开入口访问。第一版用普通 TypeScript 目录。 | 换掉一个玩法，变更集中在它自己的功能目录、资源和装配清单。 |
| 资源交付包 | 按玩家何时需要内容分组。启动资源本地交付，章节或独立模式按需加载，多处使用的大资源按实际首次使用点归组。 | 看导出报告中的首包、按需包和远程资源，再在目标平台验证冷启动和第一次进入该内容。 |
| 跨项目共享包 | 模板先用有版本的仓库快照分发。两款游戏开始独立升级后，再把边界稳定、确实需要同步修复的模块提取为版本包，并验证 Estella 能编译和导出该依赖。 | 旧项目能停留在已知版本，新项目能独立升级；升级说明能指出接口、资源和存档的变化。 |

如果目标还有“脚本按需下载”的要求，应单独核对该平台导出的 JavaScript 文件和启动请求。TypeScript 目录控制源码依赖，资源组控制资产交付，实际下载的脚本以导出产物为准。

**Estella 的实际交付由资源组配置决定。** `assets/boot/`、`assets/game/chapter-01/` 都是项目自定义目录。通过编辑器把目录指定为 `local`、`subpackage` 或 `remote`，结果保存在 `.esengine/asset-groups.json`。进入章节时按清单组名调用 `Assets.loadGroup`，向玩家显示进度和失败后的返回或重试入口。角色、音效、图标等仅由代码或表中 ID 动态选取时，要核实构建能收集它们，必要时对相应小目录开启 `alwaysInclude`。首屏的字体、加载界面、重试按钮应能在章节包尚未下载时独立显示。[资源组定义](https://estellaengine.com/docs/zh-cn/api-ts/index/interfaces/assetgroupdef/) · [构建与导出](https://estellaengine.com/docs/zh-cn/publishing/overview/)

项目在 [Git 忽略规则](../.gitignore) 中保留了 [资源组配置](../.esengine/asset-groups.json)。体验表从 CSV 经 Luban 生成 TypeScript 和客户端 JSON，启动后按表中的组名和路径打开对应预制体。Web 成品测试检查工作台首次显示时的请求，并在首次进入样例时验证分包下载。[体验表源](../config/luban/data/experiences.csv) · [导出包测试](../tests/web-smoke.mjs)

## UI 管理器

**需要一个项目级 UI 导航入口，建议叫 `UIRouter`。** 本地 SDK 的 `UIPages` 已具备页面注册、预加载、异步打开、关闭，以及关闭时保留或销毁的策略。控件、布局、焦点和基本对话框也有引擎实现。项目负责决定哪一页可见、谁接收返回、何时允许底层操作。路由按当前 UI 所在的 World 持有页面实例，页面标识和展示策略可在项目级登记。[Estella UIPages](https://estellaengine.com/docs/zh-cn/api-ts/index/classes/uipages/) · [UI 交互](https://estellaengine.com/docs/zh-cn/ui/interaction/)

| 显示层 | 用途 | 输入与生命周期 |
|---|---|---|
| HUD | 血条、计时、操作提示等场内信息 | 跟随当前玩法；交互区域消费对应输入。 |
| Page | 主菜单、设置、选关等整页界面 | 维护页面历史，返回时恢复前页和焦点。 |
| Modal | 确认、选择、错误对话框 | 顶层弹窗接收确认和返回；关闭后焦点回到打开它的控件。 |
| Overlay | 短提示、加载进度、转场遮罩 | 短提示允许输入穿过；阻塞式加载遮罩显式接管输入。 |

建议对功能模块公开页面导航、返回、请求弹窗和发送提示这几类操作。由启用的功能登记自己的页面标识、预制体和关闭策略。每个页面自行绑定显示数据，业务动作交给所属功能。比如从暂停菜单打开设置，再点“恢复默认”，第一次返回关闭确认框，第二次返回暂停菜单，玩家选择继续后才恢复游戏时间。这一条路径同时验证弹窗顺序、焦点和暂停的归属。切场景或快速返回时，已失效的异步开页结果应随页面或场景释放。

## 公共能力与归属

**资源与状态的拥有者。** 启动场景持有 Canvas，每次导航持有自己的预制体、输入订阅和分包收据。加载请求可以被取消，异步完成时只允许当前请求进入导航栈。原生玩法场景采用 `loadAdditive` 和配对卸载，其他界面可以跨场景使用。暂停菜单、切后台、加载三个原因分别登记到 `GameSession`；需要暂停的 ECS 玩法系统读取 `running`。[导航栈](../src/framework/ui/router.ts) · [场景生命周期](../src/framework/flow/scene.ts)

**故障与恢复。** 启动加载和错误提示使用独立的原生控件，首页预制体缺失时也可重试。必需资源失败会清理对应引用的失败缓存，重试可以重新访问宿主。无法解码或版本更高的存档保留原值并进入只读模式。异步存储确认失败会回读宿主实际可见值，玩家可点击设置页提示重试。[资源加载](../src/framework/content/assets.ts) · [存档槽](../src/framework/storage/slot.ts)

下表给出首版和后续产品的职责。首版 UI 实现 HUD、页面和模态栈、焦点恢复、可穿透的短提示、阻塞加载遮罩、中英文与大字号。样例计时器属于 HUD，保存设置后显示短提示。具体玩法、渠道登录、运营服务，以及面向目标设备的性能预算随产品扩展。

| 能力 | 模板负责的决定 | 归属与接入时机 |
|---|---|---|
| 启动与流程 | 初始化顺序、启动失败的可见状态、切场景期间的取消与重试。具体菜单和玩法流程由每款游戏装配。 | 首版，`app` 和 `framework/flow`，调用引擎 `SceneManager`。 |
| 生命周期与时间 | 区分应用、玩家档案、一局或场景、页面四种使用期。资源、订阅和计时任务由创建方或接管方清理。区分游戏暂停、界面时间和应用切后台。 | 首版约定；场景资产使用引擎 `AssetScope` 和场景的资源接管能力。 |
| 输入与设备 | 以“确认、返回、移动”等动作接线，页面和弹窗有明确优先级。具体玩法拥有自己的动作集合。 | 首版接入 `InputMap`；改键、手柄提示、触控布局随目标设备启用。 |
| 资源与内存 | 定义首屏必需资源、按需资源、共享资源的拥有者，以及加载失败后的处理。 | 首版，`framework/content`。反复进入、退出同一内容时检查常驻内存。 |
| 设置、音频与语言 | 设置默认值、音量分组、静音、语言回退，以及修改后何时生效和保存。业务界面通过文本键取文案。 | 首版可选 `modules/settings`，接入 `AudioMixer`、`Localization`。主题、语音与译文由产品提供。 |
| 存档与兼容 | 每款游戏的键前缀、设备设置与玩家进度的归属、稳定内容 ID、存档版本、迁移和读写失败行为。 | 首版，使用引擎 `SaveManager`。玩法拥有自己的数据结构和迁移样本，持久化使用稳定 ID。 |
| 配置与内容生产 | 确定表的来源和生成方式，检查重复 ID、跨表引用、资源缺失和缺少的文本键。错误能定位到具体表、行或资源。 | 首版，`config/luban`、`src/gen`、`assets/data`、`tools`。 |
| 模块通信 | 需要结果的动作调用所属模块的函数；已经发生且允许多个订阅者响应的事实使用有类型的事件。例如保存设置成功后才广播设置已更改。 | 首版约定，沿用 ECS 资源和引擎事件。页面关闭时解除其订阅。 |
| 平台与设备能力 | 保存、输入等已有引擎覆盖的功能直接接入；登录、成就、分享、触感等按本作需要定义最小接口。 | 发布到相关平台时添加 `platform` 实现。能力不可用时，界面能走本地路径。 |
| 可访问性与适配 | 菜单焦点顺序、文本放大、长译文、音量分类、对颜色与声音提示的替代方式。 | 焦点、字号与可缩放布局进入首版 UI 规范；字幕、减弱动态效果等随内容启用。 |
| 诊断、构建与回归 | 故障记录带构建号、场景、模块和资源组。提供干净构建、内容校验、旧档读取和导出包冒烟入口。 | 首版建最短验证路径，目标平台确定后记录首屏时间、慢帧、内存峰值和首包大小。 |

**按游戏类型选装的能力**包括背包、经济、任务、技能、战斗、对话、新手引导、回放、联机同步，以及运营活动。第一次使用可放在 `game/features`，第二款有相同规则时再抽出可复用部分。对象池、空间索引和流送策略有具体性能指标可测时再引入。在线运营型项目还要设计账号身份、服务端数据权威、内容版本匹配、活动开关与回退。成就、排行榜、支付、广告按发布渠道接入，各玩法只依赖实际用到的能力。

| 公开实践 | 转化为本模板的决定 |
|---|---|

| Bungie 在《Destiny》的开发中处理过多个功能分支并行制作内容、构建缓存和内容合并问题。[Bungie 的 GDC 分享](https://www.gdcvault.com/play/1025992/Pipeline-Support-for-Feature-Branches) | 先落实内容源、稳定 ID、资产元数据和引用校验。设计师改表后可以自行生成、预览和定位错误。团队并行制作量上来后再投资增量构建与缓存。 |
| Riot 改造《VALORANT》UI 时覆盖了从启动到结算的玩家路径，还测试切换窗口、帧率变化和不同配置的硬件。[Riot 的 UI 改造复盘](https://playvalorant.com/en-us/news/dev/performance-boost-valorant-s-global-invalidation/) | 模板保留跨界面、跨生命周期的冒烟用例，加入弹窗中切后台、加载中返回、连续切场景三个故障场景。每款游戏选一台代表性低配设备建立基线。 |
| Xbox 的无障碍指南分别讨论文字、导航和焦点；Valve 的 Steamworks 允许用独立测试分支分发构建。[Xbox 指南](https://learn.microsoft.com/en-us/xbox/accessibility/guidelines) · [Steamworks 测试分支](https://partner.steamgames.com/doc/store/application/branches) | 把焦点与文本缩放写进公共 UI 的验收条件。准备发布的构建有独立版本和可追溯产物，先在测试渠道验证，再晋级正式渠道。 |

## 实施顺序与模板验收

1. **先证明框架可以换游戏。** 从应用入口启用设置模块，用同一套 UI 打开设置、修改音量、返回、重启后读回。注册另一套玩法或空场景，确认设置模块可复用。暂停、胜负、章节等具体规则由本作声明。
2. **再证明内容可以交付。** 建一个本地启动组和一个按需内容组，带上一张配置表。验证首包依赖、按需加载、失败重试、加载中返回，以及干净副本的实际导出。
3. **最后证明模板可以升级。** 保留一份旧版本存档、一次构建的包体及性能基线和一条 MCP 冒烟用例。复制模板后更换游戏标识，确认存档隔离；升级框架后重跑相同用例。模板版本、游戏构建号、内容版本和存档结构版本各自记录，便于判断两版游戏能否共用同一份内容或进度。

首版完成的标志是另一款游戏能够独立选择功能、替换玩法和资产、导出成品，并在下一次框架升级时验证已有内容。每款游戏可以据目标玩家和设备自行扩展这套结构。
